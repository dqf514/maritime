3 · 发现并修复的 4 个真实并发缺陷

压测不是为了拿好看的延迟，而是把真实缺陷逼出来。本轮发现 4 个、修复 4 个、全部复测通过，模式统一为 「读-判-写（TOCTOU）→ 数据库层原子条件更新（atomic claim）」：在 SQLite 写锁与 PostgreSQL 行锁下均正确。

D1 · 资金安全

发票并发付款「双花」（重复收款）

位置：services/finance_workflow.py · record_payment ｜ 场景 S4 ｜ 严重度：高（资金）
现象
25 线程同时全额支付同一张发票，多笔请求同时通过「未超付」检查 → 发票被多次入账、Payment 重复落行。
根因
经典 TOCTOU：先读 paid_amount 判断余额，再更新。并发下 25 个线程读到同一快照，全部放行。
修复
改为原子条件更新：单条 UPDATE … SET paid_amount = paid_amount + :amt WHERE id=… AND status IN (issued, partially_paid) AND paid_amount + :amt <= total； claimed != 1 时刷新行并按现场状态抛 409 INVALID_STATE / OVERPAYMENT（保持既有测试契约），成功后再插 Payment 行。
复测
1×200 / 24×409，收款合计 = 发票金额（7777.00），Payment 恰 1 条 — 零多收。
D2 · 状态机竞争

租约激活竞态 → 航次号唯一键 500

位置：routers/commercial.py · charter_transition ｜ 场景 S3 ｜ 严重度：高（500 + 脏数据）
现象
25 线程同时把同一租约推进到 active，多个线程同时执行「自动创建关联航次」副作用 → UNIQUE constraint failed: voyages.tenant_id, voyages.voyage_no，整批 500。
根因
状态检查（transition() 合法性判断）与状态写入之间没有互斥；多线程同时判定「可以激活」，重复触发副作用。
修复
transition() 之后立即做原子认领： UPDATE charters SET status=:next WHERE id=… AND status=:expected；claimed != 1 → 干净的 409 INVALID_STATE，不再进入副作用。
复测
两阶段各 1×200 / 24×409，最终状态 = active，无 500。
D3 · 唯一约束竞争

COA 并发分摊 → 500（coa_allocations.lifting_id）

位置：routers/coa.py · allocate_lifting ｜ 场景 S5 ｜ 严重度：中
现象
25 线程同时把同一 lifting 分摊到同一行程，预检查全部通过后同时插入 → 唯一约束炸出未处理 500。
根因
「是否已分摊」预检查是读操作，数据库约束是真正的守门人，但 IntegrityError 没被捕获翻译。
修复
路由捕获 IntegrityError → db.rollback() → 命中 coa_allocations 时返回 422 LIFTING_ALREADY_ALLOCATED。
复测
1×200 / 24×422，分摊守恒 remaining_qty = 0。
D4 · 幂等语义

并发删除同一挂靠港 → 3 个 200（应仅 1 个）

位置：routers/operations.py · delete_port_call ｜ 场景 S6 ｜ 严重度：中
现象
25 线程同时软删除同一挂靠港，多个线程同时看到 deleted_at IS NULL 并各返回 200。
根因
删除前的「是否已删」是读-判-写，软删除幂等语义在并发下失守（回收站/审计口径不一致）。
修复
原子认领 UPDATE port_calls SET deleted_at=:now WHERE id=… AND tenant_id=… AND deleted_at IS NULL；claimed != 1 → 404。
复测
1×200 / 24×404。
为什么这 4 个缺陷重要：它们都是「平时单用户点不出来、上并发就出事」的那类问题——双花直接是资金事故， 另外三个会造成 500/脏数据/审计口径错乱。统一修复模式（原子条件 UPDATE 认领）已在 SQLite 与 PostgreSQL 两种锁模型下成立， 并被新增测试覆盖。

画像解读

  • 读表现健康：混合读 p50 171ms、45 rps，全部 200。列表页数据接口在此负载下毫无压力。
  • 写在 SQLite 下强串行：所有写场景 p50 都 ≈ 2.2s——这正是「25 个写请求排队过单写者锁」的典型形状 （单请求写本身几十 ms，排队吃掉了 2.1s）。SQLite rollback-journal 模式写独占，写锁期间还会挤占读： S2 的 p95 2.1s 长尾就是读请求撞上写事务的体现。
  • 登录 p50 2.5s 偏慢：密码哈希校验 + 每次登录写 last_login_at，25 并发下同样进入写串行队列。单用户体感 <400ms，可接受；优化见第 8 节。
  • S7 并行独立写全成功：25 条「创建估算→TCE 计算」链路 100% 成功，说明写引擎本身在竞争下不丢不错，纯粹是排队延迟。
  • 正确性 > 性能：错误码分布全部是设计中的受控 4xx，没有任何 5xx——这正是压测想要的「失败得有规矩」。
容量结论（当前 SQLite 部署）：25 并发写是安全的（不出错），但写延迟会随并发近似线性排队。 生产多用户环境按 compose 模板切 PostgreSQL 后，行级锁 + WAL 读写并行可直接消除写排队与读长尾（见 P0-4）。

6 · 同/异步刷新与加载体验审计

用户问的是三件事：页面刷新怎么做的（同步还是异步）、等待时有没有友好的加载动画、体验够不够大厂。 我们做了两层审计：运行时探测（人为把 API 拖慢 1.5s，看页面给用户显示什么）与代码走查（全前端扫描）。
